# ESP3 投递根因分析：ESP1 无线入口观测

2026-09-26，TZ 确认 ESP1、ESP3 同时连接电脑，授权继续根因分析，并授权必要的诊断固件生成与刷写。

本轮只为 ESP1 增加临时、默认关闭的无线观测。ESP3 固件、TGR1 广播、签名、采样、75 秒 freshness、Bark 和腾讯心跳合同保持不变。ESP1 接收相关协议和业务状态不由观测模块更新。

## 实验与边界

- 先采集现有固件 ESP3 TX、电脑 UDP 旁路、ESP1 DIAG 三路基线。
- 诊断镜像 `esp1-air-observe-20260926.1` 保持 Wi-Fi 省电关闭。USB 显式启动观测后，只保留与本机私密登记中 ESP3 对应的基础设施数据帧元数据；原始帧、地址、温度、密钥均不保存或输出。
- 元数据包括上/下行、组播位、是否经过 ESP1 当前关联 AP、802.11 序号、重传位、加密位、长度、接收信号强度。802.11 序号不是 TGR1 序号，加密帧不能凭这些元数据证明某一 TGR1 内容已到达。
- 观测采用固定容量队列，Wi-Fi 回调不分配内存、不输出串口。溢出计数必须纳入证据。最多 10 分钟自动停止，断开 Wi-Fi 同样停止；显式停止后恢复非混杂模式。
- 混杂模式可能改变接收表现。因此比较关闭/开启/关闭窗口；症状在开启时消失只能说明观测干预相关，不能直接当作修复或唯一根因。
- 优先只刷 ESP1 app 分区；不写引导程序、分区表或 NVS。刷前重新核对登记 MCU 身份、串口唯一所有者、镜像哈希。原已构建镜像本机保存于 `.build/esp1-wifi-ps-none-20260925.1-before-air.bin`。

### 结论与下一步

本轮确认当前 ESP3 上行和 AP 下行经过 ESP1 当前关联的同一个 AP，并建立了无线入口与 UDP 接收之间的观测能力。但是两个窗口都没有复现昨天的间歇性漏收，不能确定唯一根因，也不能把这份诊断固件称为修复版本。仍未排除间歇性 AP 广播转发、空口接收或 ESP1 驱动/协议栈问题。

下一步需要故障复现窗口中的同步证据。若能提供 AP 型号、拓扑及单客户端转发计数，可先做网络侧只读核对；否则保持单次设备会话做更长的同步采集。即使空口观测没有帧，也不能单独区分 AP 未发与 ESP1 未能在空口收到。若观察到相关下行帧而应用不收，再针对驱动/解密/UDP 路径设计更窄的实验；若改用单播对照，须将其保留在诊断路径，不能借此直接变更正式 TGR1 合同。

当前 ESP1 留在默认关闭无线观测的诊断镜像；ESP3 固件未变。没有验证手机 Bark 收件、Tab5 实屏、云端查询或长期稳定性。未执行 Git 暂存、提交或推送；原 handover 的既有修改保持原样。
