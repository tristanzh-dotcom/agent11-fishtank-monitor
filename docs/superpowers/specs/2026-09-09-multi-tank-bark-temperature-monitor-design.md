# 四缸五探头本地 Bark 监测与定时温度汇总设计

**日期：** 2026-09-09
**状态：** 2026-09-12 超时与日报计时修正已实现，完成源码核对、既有日报主机测试和目标构建；实机网络时序待验证。Tab5 已列入刷写范围记录，既有授权与现场验收待核对；现场 ROM 待接入
**项目：** Agent11 Fish-Tank Monitor

## 1. 目标与边界

### 目标

在现有“包包缸主缸 + 回水缸”两个 DS18B20 的基础上，增加三个小缸探头：

1. 老四缸；
2. 小黑缸；
3. 毛毛缸。

系统最终读取五个温度点：

- 包包缸主缸；
- 包包缸回水缸；
- 老四缸；
- 小黑缸；
- 毛毛缸。

三个小缸需要拥有独立的温度告警、探头故障、提醒和恢复生命周期，并通过设备直连
Bark 通知。每天上海时间 09:00 和 18:00 额外发送一条包含五个温度读数的 Bark 汇总，
该汇总在触发和投递队列上独立于温度告警。

### 明确边界

- 三个小缸的温度与小缸事件不进入 Agent11 当前的 `FishTankStateV1` 公共状态。
- 不修改 Agent12/Web 页面、腾讯 SCF 状态投影或现有只读 GET 合同。
- 不把回水缸改成独立高低温安全告警源；它仍是循环诊断和日报数据源。
- 不控制加热棒、水泵、插排、灯光或任何市电设备。
- 不把 Bark Device Key、Wi-Fi 凭据、腾讯设备密钥或 CA 写入设计文档、日志、URL 或
  生成物。

## 2. 当前基线与设计原因

现有固件是单设备 `tank01` 的双探头实现：

- `GPIO4` 上使用一条 OneWire 总线；
- `Ds18b20Reader` 读取固定的主缸和回水缸 ROM；
- `TemperatureSample` 只有 `display_c` 与 `return_c` 两个值；
- 一个 `TemperatureEngine` 管理主缸高低温、快速温变、探头故障和主缸/回水温差；
- `ActiveEventSnapshot` 按事件类型保存活跃事件；
- Bark 指纹当前包含 aquarium、设备标识和事件类型，但未写入请求 JSON，也未用于队列去重；
- 心跳合同固定发送 `main_c`、`sump_c` 和现有主缸活跃事件。

若多缸共用一个状态机，计时和事件状态会混用；若共用按类型索引的 `ActiveEventSnapshot`，
同类事件会互相覆盖。现有直连 Bark 文案也没有鱼缸名称，无法区分来源。因此本设计
保持现有主缸/回水缸公共链路稳定，在设备内部增加一个不向 Web 投影的本地监测域。

仓库 SCF 还存在按 `BARK_KEY` 配置启用的温度通知路径：心跳处理器对新打开或升级的
主缸事件发送 Bark。本次保持该路径，不处理主缸可能存在的双路径通知；此次审计未核验
线上配置是否启用。代码依据为 `cloud/tencent-scf/src/scf_runtime.mjs` 和
`cloud/tencent-scf/src/heartbeat_handler.mjs`。

## 3. 方案比较与选型

### 方案 A：本地五路读取 + 小缸直连 Bark（采用）

ESP32 一次转换并读取五个探头。主缸/回水缸继续使用当前链路；三个小缸各自运行独立
的温度状态机，事件经带鱼缸身份的本地 Bark 队列投递。日报直接由 ESP32 按上海本地
时间生成。

优点是改动范围最小、无新增云端合同、无 Web 页面变化，并且温度告警仍不依赖常驻电脑
或 Agent 服务。缺点是设备断电或长期离线时不能保证日报按时送达。

### 方案 B：扩展心跳和 SCF，由云端定时发日报

ESP32 把三个小缸读数上传到私有云状态，SCF 定时任务在 09:00/18:00 读取并发送 Bark。

该方案可以集中管理定时任务，但需要扩展心跳载荷、COS 内部状态、云端部署和重试语义；
还会增加“云端快照新鲜度”和“日报是否使用过期读数”的产品规则。本次需求不需要这些
额外复杂度，因此不采用。

### 方案 C：把五路读数全部扩展为公共 Web 状态

这会让 Agent12/Web 看到三个小缸，并要求修改公共 schema、SCF 投影和下游页面。它与
“不需要 Web Agent 页面显示”的范围相冲突，排除。

## 4. 物理与传感器设计

### 4.1 总线

五个 DS18B20 共用现有 `GPIO4` OneWire 总线。采样继续采用 30 秒周期和 12-bit 分辨率；
一次 `requestTemperatures()` 后读取五个固定 ROM。12-bit 转换时间约为 750 ms，相对
30 秒采样周期不会成为吞吐瓶颈。

现场采用三线供电模式：

- VCC 接 3.3V；
- GND 接公共地；
- DATA 接 GPIO4；
- 总线保留一只位于控制端的 4.7kΩ 上拉电阻。

线缆优先采用一条主干加短分支，避免五个长线形成大范围星形拓扑。控制盒留在底柜外侧，
每条入水线保留滴水弯。增加传感器后，线缆总长度、分支和干扰情况必须通过真实串口
连续采样验证，不能仅由“能发现 ROM”推导长期稳定。

### 4.2 ROM 与角色绑定

启动时继续打印所有探头的发现数量和 ROM。完成物理识别后，将 ROM 固定绑定到以下逻辑
角色，不能依赖 OneWire 发现顺序：

| 逻辑键 | 中文名称 | 监测用途 | 当前 ROM 状态 |
| --- | --- | --- | --- |
| `main_tank` | 包包缸主缸 | 高低温安全告警、日报、现有 Web 主缸值 | 已固定，沿用当前配置 |
| `sump_return` | 包包缸回水缸 | 循环温差诊断、日报、现有 Web 回水值 | 已固定，沿用当前配置 |
| `laosi_tank` | 老四缸 | 独立高低温告警、日报 | 待现场扫描后固定 |
| `xiaohei_tank` | 小黑缸 | 独立高低温告警、日报 | 待现场扫描后固定 |
| `maomao_tank` | 毛毛缸 | 独立高低温告警、日报 | 待现场扫描后固定 |

三个新探头只允许按固定 ROM 读取，不继承现有读取器在未配置时按发现顺序回退的行为。
新增配置须与全部五个角色比较，拒绝重复 ROM；不得覆盖既有主缸/回水缸绑定。

- 未绑定的小缸显示“未配置”，不进入温度状态机。
- 重复绑定的小缸显示“配置错误”，不读取、不进入状态机，现场启用前必须修正。
- 已正确绑定但读取失败的小缸提供无效样本，按连续两次无效规则触发探头故障。
- 不自动换用其他探头；配置问题不阻止已有正确配置角色继续监测。

禁止将测试地址作为实物绑定。隔离主机测试可以使用明确标注的模拟 ROM；三个新实物
ROM 必须现场扫描、人工确认后才能写入正式配置。串口发现信息仅用于本地识别。

## 5. 温度策略

### 5.1 高低温阈值

高低温持续时间沿用当前策略：N2 候选持续 15 分钟，N3 候选持续 5 分钟，恢复条件持续 15
分钟。状态机每 60 分钟最多生成一次重复提醒候选；当前 Bark 规则只重复发送 N3 温度告警
和探头故障，普通 N2 温度告警不重复，严重告警最多重复两次。

| 监测点 | 低温 N2 | 低温 N3 | 低温恢复 | 高温 N2 | 高温 N3 | 高温恢复 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 包包缸主缸 | `<23.5°C` | `<22.5°C` | `>=24.5°C` | `>27.5°C` | `>28.5°C` | `<=26.5°C` |
| 老四缸 | `<22.5°C` | `<20.5°C` | `>=23.5°C` | `>27.5°C` | `>28.5°C` | `<=26.5°C` |
| 小黑缸 | `<23.5°C` | `<22.5°C` | `>=24.5°C` | `>27.5°C` | `>28.5°C` | `<=26.5°C` |
| 毛毛缸 | `<23.5°C` | `<22.5°C` | `>=24.5°C` | `>27.5°C` | `>28.5°C` | `<=26.5°C` |

老四缸的 `23.5°C` 低温恢复阈值是本次 TZ 已确认的设计决定：它保持与自身 N2 低温
阈值相差 1°C 的滞回，而不是复用其他鱼缸的 `24.5°C`。

### 5.2 事件类型

包包缸主缸继续沿用当前全部事件语义，包括高温、低温、严重高低温、快速温变、主缸
探头故障和主缸/回水温差。

三个小缸各自复用单探头可适用的状态机：

- 高温、严重高温；
- 低温、严重低温；
- 快速温变；
- 探头故障；
- 不产生双探头 `temperature_gradient` 事件。

小缸探头连续两次无效时打开 `sensor_fault`；故障期间不把旧温度当作恢复证据；首个有效
读数发送故障恢复，并重新开始温度恢复观察。每个小缸的状态机必须独立保存候选、恢复、
提醒和峰值等级状态。

快速温变完整规则沿用 `2026-07-19-temperature-event-closure-design.md`：30 分钟窗口
变化达到 1°C 打开 N2，达到 2°C 升级 N3，窗口变化小于 1°C 连续保持 30 分钟后按最高
等级恢复；无效读数中断历史与恢复观察。第 5.1 节的 15 分钟恢复不适用于快速温变。
既有高低温事件类型及 opened/resolved 语义保持原样，不统一改造成快速温变的升级模型。

### 5.3 ESP2 状态更新中断

2026-09-23，经 TZ 明确批准，由 ESP1 使用现有局域网接收状态监测 ESP2 的状态更新：

- ESP1 至少接收过一条有效 ESP2 状态后，超过现有 75 秒新鲜度期限仍未收到更新，发送一次
  “温控ESP2号连接中断” Bark；收到新鲜状态后发送一次恢复 Bark；同一状态期间不重复提醒。
- ESP1 尚未收到过有效 ESP2 状态时不告警，避免设备启动顺序造成误报。
- 该通知表示 ESP1 收不到 ESP2 状态更新，不判断断线原因，也不替代温度探头故障通知。
- 复用现有 ESP2 局域网状态包和 Bark 通道，不改 72 字节传输格式、SCF 心跳或公共状态合同。
- 监测锁存仅在 ESP1 本次运行期间有效。每次状态转换尝试发送一次；Bark 请求失败不增加新重试队列。
- 2026-09-24，为断联原因分析，ESP1 在独立 `net_diag` Preferences 命名空间保留最多 32 条低频诊断记录，包含自身 Wi-Fi 状态、主循环长停顿及 ESP2 状态过期/恢复；不记录逐包间隔，不改变上述 Bark 行为或断联判断。

## 6. 固件内部结构

### 6.1 读取层

读取层增加五路带身份的最新读数集合。每个值使用可空类型：无效读数为 `nullopt`，不
复用上一次温度。

为保持当前公共心跳合同稳定，主缸/回水缸仍生成现有 `TemperatureSample`；三个小缸
直接以 `TemperatureSample{at_ms, 小缸温度, std::nullopt}` 进入各自的
`TemperatureEngine`，无需新增引擎采样接口。回水值始终为空，使小缸不打开温差事件。
五路读数及配置状态组成一个仅驻留内存的本轮快照，供日报使用。

### 6.2 状态机与事件身份

保留现有主缸 `TemperatureEngine` 和 `ActiveEventSnapshot` 的公共行为。三个小缸各有
一个独立 `TemperatureEngine` 实例。

小缸事件来源用以下组合标识：

```text
tank_key + event_type
```

队列元素保留鱼缸键及完整事件（类型、状态、等级、时间、温度），中文名称由固定配置
查表获得。独立引擎管理生命周期；队列按产生顺序保存，不用上述组合键合并 opened、
escalated、reminder、resolved，也不吞掉恢复后再次打开的事件。不增加通用去重系统。

小缸事件不调用 `ActiveEventSnapshot::apply()`，因此不会进入心跳或公共状态投影。

### 6.3 Bark 投递

采用三处有界 RAM 存储：主缸原有 16 条队列；三个小缸共用一条 16 条队列，每条携带
鱼缸身份；日报使用一个独立待发槽位。小缸队列满时沿用现有拒绝新入队、增加丢弃计数
的策略，不移除旧事件、不改变引擎状态；计数保留在本地诊断。有限 RAM 不保证长时间
离线期间全部事件保留，共用小缸队列也不承诺小缸之间投递故障完全隔离。

每个 30 秒采样轮先完成五路读取、各引擎判断与日报快照生成，再最多尝试一次告警 Bark。
主缸与小缸队列同时非空时轮流选取，失败后下一轮仍切换，避免一个失败队首饿死另一条
队列；仅一条非空时选择该条。HTTP 2xx 只确认选中队首，失败保持队首，下一采样轮再试。
不为每缸复制网络组件，不增加线程框架。

日报仅在两条告警队列均为空且本轮没有尝试告警时发送，本轮最多一次 Bark 尝试；持续
告警积压可使日报过期，按第 7.3 节丢弃。心跳仍按既有节奏独立判断。同步 HTTPS 会占用
主循环，独立槽位不能保证零延迟；主缸告警、小缸告警、日报及现有心跳 HTTPS 均须显式
设置 TCP 连接、TLS 握手和响应读写超时，各为 5 秒。TLS 握手超时须单独设置，不能用
连接或读写超时替代，也不能沿用库的 120 秒默认值。这些是各阶段超时，不代表整个请求
总耗时不超过 5 秒；验证失败路径的等待受限，并检查采样、心跳仍持续推进。

实际 Bark 标题或正文必须包含包包缸/老四缸/小黑缸/毛毛缸名称。故障 opened/reminder
显示“无有效读数”，不打印引擎内部的 `0.0` 占位；故障 resolved 显示恢复后的有效读数。
该处理放在消息格式化层，无需重构引擎事件类型。普通温度事件显示事件发生时的读数。
日报等级为 `active`，告警等级沿用现有直连 Bark 规则。

内部 fingerprint 若保留只作标识，不能声称它实现了手机端或服务端去重。HTTP 成功是
投递接口确认，不等同于手机已阅读；响应丢失后的重试可能重复通知。JSON 继续安全转义，
凭据不进入 URL、标题、正文或日志。

## 7. 每日 09:00/18:00 温度汇总

### 7.1 触发

设备使用 NTP 同步后的 UTC epoch 转换为 `Asia/Shanghai` 本地时间，在每天两个固定时段
生成汇总：

- 09:00；
- 18:00。

触发窗口分别为 `[09:00:00, 09:01:00)` 和 `[18:00:00, 18:01:00)`。在窗口内首个
完成五路采样且时间已同步的调度机会生成一条汇总，允许 09:00:20 生成；全部探头缺测
也可以生成缺测报告。消息记录该轮实际采样时间。窗口外不补采，09:10 才校时不发早报。

时段键为上海日期加早/晚时段，在生成时即记录，失败重试复用同一快照。在连续运行期间
按时段先后维护已处理位置，时间回拨不重发已处理时段；前跳越过窗口则跳过。没有有效
时间不生成，不从云端或 Web 取值。本期不承诺跨重启去重。

### 7.2 消息内容

日报使用一条普通 Bark 通知，独立分组，例如：

```text
鱼缸温度提醒｜2026-09-09 09:00
采样时间：2026-09-09 09:00:20（上海时间）

包包缸（主缸 / 回水缸）
  主缸：22.1°C（温度偏低）
  回水缸：21.8°C
老四缸：22.1°C（温度偏低）
小黑缸：28.7°C（温度严重偏高）
毛毛缸：20.1°C（温度严重偏低）
```

上例仅为格式示例。已绑定但读数无效显示“无有效读数”，未绑定显示“未配置”，重复
绑定显示“配置错误”；不使用旧值或模拟值。包包缸主缸与回水缸作为同一鱼缸组展示，
其余三缸各自独立展示。主缸及三只小缸按各自当前温度阈值标注正常、偏低/偏高或严重
偏低/偏高；正常时不显示状态，回水缸只显示温度。该状态是采样时的即时温度分类，不
代表已满足持续时间、已经触发或解除告警；日报只表达该次五路采样，不复制报警事件状态。

### 7.3 断网、重启与补发边界

本期采用以下最小可靠性边界：

- 时间有效且窗口内完成采样时，即使 Wi-Fi 暂断也可保存快照到独立 RAM 槽位；
- 发送失败按第 6.3 节重试，正文始终保留原采样时间和温度，不换成重试时的新读数；
- 从生成时刻起用单调时钟计时，满 10 分钟清除待发槽位，不再开始发送；不跨到晚报补发；
- 生成待发记录时读取当前单调时间建立截止点；每次实际调用日报发送前再次读取当前单调
  时间检查过期，不复用本轮开始时的 `now_ms`。该计时修正不改变快照中的采样时间或温度；
- 错过窗口（断电、未校时或无采样机会）不补采历史温度；
- 重启会清空当前未投递的 RAM 汇总，和现有温度事件队列的行为保持一致；
- 重启也会清空当前运行的时段去重标记，因此跨重启不保证绝不重复；
- 不把下一次采样冒充为错过时段的“当时温度”。

窗口内重启后，如重新校时并完成采样，可以生成该窗口的新快照，可能重复；窗口外
重启不补发。10 分钟截止约束发送尝试开始时间，已开始的请求仍受网络超时限制。

如果后续要求断电后也必须补发，需要另行批准 NVS 中保存“时段键 + 五路采样快照”的
持久化设计；这不属于本期实现范围。

## 8. Web、心跳与云端边界

本期不修改以下内容：

- `HeartbeatPayload` 的 `main_c`、`sump_c` 字段；
- `ActiveEventSnapshot` 的公共事件列表；
- `FishTankStateV1` schema；
- 腾讯 SCF 心跳校验、COS 状态投影和只读 GET；
- Agent12/Web 页面和轮询器。

因此 Web 仍只看到包包缸主缸/回水缸的既有状态；三个小缸存在于 ESP32 本地采样、本地
告警、日报消息和签名的 Tab5 局域网显示包中。设备离线状态仍由现有主设备心跳链路表达，
不为每个小缸创建云端设备身份。

## 9. 验收设计

### 9.1 主机测试

选取直接受影响的主机测试及合同回归：

1. 五路逻辑键、ROM 唯一性、未绑定/重复绑定/读取失败及禁止发现顺序回退；
2. 四个报警缸的阈值矩阵，特别是老四缸 `22.5/20.5/23.5°C`；
3. 每个小缸独立打开、升级、提醒、恢复和再次打开；
4. 实际 Bark 请求 JSON 包含正确鱼缸名称；故障不显示 0°C；队列不合并生命周期消息；
5. 小缸故障不进入 `ActiveEventSnapshot` 和心跳 JSON；
6. 五路日报格式、无效值表达和普通 Bark 等级；
7. 两个一分钟窗口、连续运行去重、未校时/错过窗口、时间回拨/前跳、重启边界；
8. 日报快照不随重试改变、10 分钟过期、队列满拒绝及计数、轮流发送与告警优先；
9. 现有双探头温度、事件快照、心跳载荷和受影响的 Bark 合同回归通过。

SCF 实现及合同未变，不默认执行云端全套测试；通过固件心跳序列化回归确认小缸数据
没有进入公共载荷。只有实际修改或证据表明影响扩大时，再按治理选择相应验证范围。

### 9.2 固件构建

在传感器 ROM 写入前先完成主机测试。随后从项目拥有目录运行现有 PlatformIO
`waveshare_esp32s3_n16r8` 构建；构建通过不等同于硬件验收，也不授权上传。

当前工作区另含 Tab5 局域网状态广播及 `tab5_lan_secret.hpp` 本机依赖。2026-09-15
经 TZ 明确要求，广播增加一个签名的 v2 扩展包，携带三路小缸读数和来源侧即时温度分类；
Tab5 同时保留旧 v1 包解析，以便过渡。该扩展只服务本地鱼缸页面，不写入
`FishTankStateV1`、云端状态或 Web 页面。刷写清单须注明产物是否包含该改动；构建成功仍
不能替代局域网接收、真实探头读数和现场验收。

### 9.3 硬件与现场门

按独立门逐项记录：

1. 五个 ROM 发现并完成人工角色确认；
2. 五路连续采样无无效值和离谱跳变；
3. 四个报警缸分别验证 Bark 告警和恢复，不改变加热系统；
4. 09:00/18:00 日报验证五路读数与无效值表达；
5. 完成安装、线缆防水和控制盒安全检查；

软件测试、云端状态、Bark 投递、上传、安装、校准和持续观察必须分开报告，不能用
主机测试或一次串口发现替代后续门。

## 10. 实施顺序与停止条件

实施时按以下顺序推进：

1. 先实现并验证主机层的多缸策略、事件身份、Bark 文案和日报调度；
2. 再扩展读取器和配置，先使用脱离现场的测试 ROM/模拟读数验证映射，不写入真实未知 ROM；
3. 生成 PlatformIO 构建证据；
4. 获得明确的目标设备和上传端口授权后，才进行硬件上传；
5. 先完成五探头桌面验证，再进入现场安装和观察。

出现以下情况时停止并保留缺口，不通过降级掩盖：

- ROM 身份无法稳定确认；
- 五路采样出现持续无效、互串或跳变；
- Bark 事件无法区分鱼缸；
- 日报时间未同步或消息内容使用了旧值冒充当前值；
- Web/SCF 合同被意外改变；
- 需要新增云资源、持久化补发或外部部署但尚未取得对应批准。
