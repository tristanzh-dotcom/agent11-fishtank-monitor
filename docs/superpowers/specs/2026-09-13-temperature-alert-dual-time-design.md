# 温度告警双时间文案设计

日期：2026-09-13

状态：已按本方案实施；软件验证与现有 SCF `$LATEST` 部署已完成，固件刷写和现场验收待后续授权。

## 1. 目标与授权范围

TZ 要求温度告警让用户“一眼获得所有重要信息”，尤其能够区别异常发生与信息发送的时间。
本次交付是设计方案，不代表代码修改、SCF 部署或固件刷写授权。

用户阅读一条通知，应能判断：哪个监测点、什么异常、告警还是提醒/解除、当时读数、事件何时判定、本次请求何时发起。
手机或 Bark 展示的接收时间不能替代前两种时间；发送发起时间也不能证明服务端受理或手机送达。

覆盖：

- 设备直推：包包缸主缸、老四缸、小黑缸、毛毛缸的既有温度及探头事件。
- 云端：既有主缸温度通知，包括现有可发送的探头故障事件。
- 包包缸的温差事件继续表达主缸与回水缸的关系，不将回水探头变成独立告警引擎。

不覆盖：日报、远程温度查询正文、云端设备离线/恢复通知、MQTT 转发备用路径、Web、Tab5。
告警阈值、持续时间、通知等级、发送频率、队列容量/顺序、重试和成功确认机制保持原有行为。

## 3. 方案选择与最小范围

采用“固定事件时间 + 每次发送发起时间”的双时间结构。

- 仅追加发送时间无法解决旧读数被误认为当前读数的问题，不采用。
- 扩展心跳传送事件日历时间，可以使云端也显示完整双时间，但会影响跨系统合同和兼容性；本期不采用。
- 不增加时间追溯服务、数据库、NVS、补发任务、延迟分级、自动丢弃或新去重系统。
- 不计算和展示两次日历时间之差；时间校准跳变不能被解释成投递耗时。
- 本期模板不附带整套阈值/持续条件列表，避免在云端复制各缸策略、把持续提醒误写为重新满足触发条件。用户重点看到状态、读数与时间。

明确限制：云端当前所有这类事件均缺少可信事件日历时间，因此事件时间栏显示“事件时间不可用”。
这是本期接受的诚实降级，不宣称已经实现云端精确事件发生时间；以后若需要补齐，应另行批准心跳合同扩展。

## 4. 用户可见文案合同

### 4.1 固定顺序

标题：`监测点｜异常类型与本次状态`。

正文：

1. 当时水温或无有效读数。
2. 本次事件判定时间。
3. 本次发送发起时间，并标明“设备”或“云端”。
4. 时间均为北京时间。
5. 一句与事件类型相关的核查建议。

标题不展示无时间限定的温度值。完整日期使用 `YYYY-MM-DD HH:mm:ss`，避免跨日、跨年查看历史通知时歧义。
温度统一一位小数和 `°C`。通知可能被 iOS 折叠或截断，设计保证重要信息靠前，不承诺所有锁屏样式无需展开便显示全文。

### 4.2 状态映射

| 事件状态 | 标题规则 | 时间栏名称 | 限制 |
| --- | --- | --- | --- |
| opened | 高温告警、严重高温告警、低温告警、严重低温告警等 | 告警判定 | 严重告警可直接打开，不能统一写“升级” |
| escalated | 对应异常“升级为严重告警” | 升级判定 | 只用于引擎真实 escalated 事件 |
| reminder | 对应异常“持续提醒” | 提醒判定 | 正文可写“截至该次判定，尚未满足解除条件”；不宣称当前仍超阈值或重新持续超限 |
| resolved | 对应异常“告警已解除” | 解除判定 | 只表达该事件在该时刻解除，不宣称其他事件或整缸安全 |

探头故障 opened/reminder 使用“无有效读数”；resolved 使用“探头已恢复”和该次有效读数。
探头恢复不等同于温度告警解除，不能合并为“鱼缸恢复正常”。

快速温变、温差事件没有保存实际变化幅度/双探头差值，本期不得补造这些值。
温差事件读数栏明确为“当时主缸水温”，不是温差值。

### 4.3 模板示例

下列温度与时间均为排版示例，不是现场测量证据。

```text
包包缸·主缸｜严重高温告警

当时水温：29.1°C
告警判定：2026-09-13 16:20:00
发送发起（设备）：2026-09-13 16:23:08
时间均为北京时间
建议：核查最新水温及加热棒温控。
```

```text
老四缸｜低温持续提醒

当时水温：22.4°C
提醒判定：2026-09-13 17:20:00
发送发起（设备）：2026-09-13 17:20:02
时间均为北京时间
截至该次判定，尚未满足解除条件。
建议：核查最新水温及加热设备。
```

```text
包包缸·主缸｜高温告警已解除

当时水温：26.4°C
解除判定：2026-09-13 16:50:00
发送发起（设备）：2026-09-13 16:50:02
时间均为北京时间
建议：继续观察水温。
```

```text
包包缸·主缸｜严重高温告警

当时水温：29.1°C
告警判定：事件时间不可用
发送发起（云端）：2026-09-13 16:25:02
时间均为北京时间
建议：核查最新水温及加热棒温控。
```

同一事件在两条原有路径上出现时，以发送发起栏的来源区分。本期不消除双路径通知。

建议按已有事件类型固定映射：高温核查最新水温/加热棒温控；低温核查最新水温/加热设备；
快速温变核查最新水温/探头位置；温差核查水流循环/探头位置；探头故障检查探头/接线；恢复继续观察。
这些都是核查建议，不发出控制命令，也不建议根据历史读数立即调整加热功率。

## 5. 时间与数据来源

### 5.1 设备事件时间

在事件生成后、进入 Bark 队列前，捕获本机 UTC 日历时间，作为本次事件判定记录。
它对应 opened/escalated/reminder/resolved 这一次判定，不是候选首次超阈值、最初异常开始或整个告警持续时间。
日历记录精度为秒，不宣称与探头转换完成时刻精确一致。

在 Bark 待发记录中附加一个可缺失的 UTC 时间值，与事件一起入队、出队；禁止用独立平行队列保存时间，以免队满或失败时错配。
该元数据不加入核心 `TemperatureEvent`、MQTT JSON、心跳 `active_events` 或公共状态合同。

时间可用至少要求本次启动已完成 SNTP 校时、时间范围合理且能安全格式化；仅大于某个 epoch 下限不等于已校时。
复用现有校时机制；若尚未暴露同步状态，仅增加最小内存状态标志，不新增校时服务或阻塞等待。
未联网不自动抹掉本次启动已校准、仍运行的时钟；本期不承诺离线长时间时钟漂移为零。

事件生成时不可用则记录缺失，正文写“时间未同步”；随后校时成功也不倒推、更改这条历史事件时间。

### 5.2 发送发起时间

设备在每次 Bark 请求构造消息时读取时钟，尽量靠近 HTTP POST；含义是开始该次发送流程，不是精确网络出包、服务端受理或手机送达时刻。
云端在 notifier 的每次 `send` 内读取可注入时钟，而非复用心跳处理开始时间；生产默认使用系统时钟，测试使用固定时钟。

格式化失败时显示“时间不可用”；设备未校时时显示“时间未同步”。时间缺失本身不能丢弃告警、阻塞采样或绕过 TLS 验证。
若既有 TLS/网络链路因未校时而发送失败，继续既有失败保留和重试，不把“生成了消息”记为送达。

### 5.3 时钟跳变与重试

- 失败重试保持原事件状态、读数、事件时间；重新读取发送发起时间。
- 校时使发送时间早于已记录事件时间时，保留原值并附注“设备时钟已调整，不能用上述时间差判断延迟”。不把历史时间强行修正到看似合理。
- 其他日历跳变也不用于计算延迟，不引入自动“历史告警”阈值。
- 重启沿用原有 RAM 队列生命周期，不跨重启恢复消息，不引入历史重建。
- Bark/手机可能乱序、延迟或重复显示。双时间提供判读依据，不承诺修复投递一致性。

### 5.4 云端事件与读数

现有事件 `atMs` 为设备单调运行时间；`sentAtMs`、`uptimeMs` 也不足以证明某次事件的固定日历时间。
禁止用 `sentAtMs - (uptimeMs - event.atMs)` 倒推、用服务器当前时间赋值，或把收到心跳时刻命名为事件判定时间。
本期云端事件判定时间固定按缺失处理。

云端正文使用 `alert.event.displayC` 作为当时读数。`alert.mainC`、`alert.sumpC` 是另一采样时刻的数据，不在本期通知正文混排。
故障事件的 `null` 显示“无有效读数”，不显示 `0°C`、NaN 或旧读数。模板只消费已有验证通过的事件。

## 7. 最小验证与验收标准

实施时按直接消费者选择 Level 2 聚焦验证；当前文档交付仅 Level 0。

| 验证项 | 必须证明 |
| --- | --- |
| 状态映射 | 普通/严重高低温、真实升级、提醒、解除按实际事件表达；不伪造高低温升级或持续超限 |
| 读数 | 一位小数、故障不显示零值、温差读数不冒充差值、云端使用事件读数而非心跳新读数 |
| 时间 | UTC 到北京时间、跨日/跨年、未校时、格式化失败均有确定输出 |
| 失败重试 | 同一消息重试事件时间不变、发送时间更新；队满/成功出队不导致时间与事件错配 |
| 校时/重启 | 未校时事件不事后补造；倒退时间有提示；重启不新增持久化恢复 |
| 云端边界 | 事件时间缺失不倒推；只改温度文案，离线/设备恢复原文案及等级保持不变 |
| 消费者回归 | MQTT 原 JSON、心跳与公共状态合同不因包装时间改变；原通知频率/队列确认规则不变 |
| 目标构建 | 改动固件后构建实际发布环境；沿用既有非 Tab5 发布边界 |

优先使用已有 C++ transport/delivery 测试与 Node `bark_notifier.test.mjs`，仅增加能证明上述边界的用例。
若 notifier 调用签名影响 heartbeat handler 或 runtime，补直接调用者的聚焦测试；不因同属云包而默认运行全套。
时间格式化采用轻量确定性实现；若抽出被日报等共同使用的 helper，才补该直接消费者回归，不主动扩大重构。

真实 Bark 验收、SCF 部署、固件刷写是后续独立阶段，须在相应命令授权范围内执行。
手机检查标题/展开正文、两条来源、历史时间可辨识；软件测试不能证明手机送达或长期稳定运行。

## 8. 审计收敛与已知限制

本设计落实方案审计的六项修正：发送含义准确、校时/缺失不伪造、删除任意延迟阈值、标题不放无时间限定温度、严格映射事件状态、同时覆盖云端温度通知。

保留并明确披露的限制：

- 云端本期没有精确事件日历时间，不通过扩展合同掩盖这一缺失。
- 现有双路径、云端事件比较机制、队列溢出/断电丢失、Bark 重复或乱序不在本期修复范围。
- 两条路径统一语义及核心模板，不新增它们原先不发送的通知类型，也不统一原有通知等级。
- 不保证历史事件代表阅读时当前状态；核查建议指向最新情况。
